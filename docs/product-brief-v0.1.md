# ClassAgent 产品初版报告 v0.1

日期：2026-09-28  
状态：产品构想；以下均为建议范围，尚未实现。

## 1. 产品定位

ClassAgent 面向需要课后回顾的学生，把课堂录音变成**可核对、可管理、可用于复习**的学习资料。它不只生成一段摘要：每个关键结论都应能定位到文字记录和对应音频，方便检查转写或 AI 理解是否准确。

一节课的主要流程：创建课程与课次 → 录音（或导入已有音频）→ 自动转写 → 生成智能纪要 → 人工校订 → 按课程归档、搜索和复习。

## 2. 目标用户与主要场景

首要用户是大学生、自学课程学习者。典型场景包括：

- 上课时专注听讲，不必一边抄写所有内容；课后快速了解本节讲了什么。
- 缺席或听不清某一段时，按主题找到原文并回听。
- 考前把同一课程的多节课串起来复习，找出概念、例题和待解决问题。

首版先服务**个人使用**；班级协作、教师端和机构管理暂不进入首版。

## 3. 功能建议与优先级

| 优先级 | 功能 | 用户能得到什么 | 首版边界 |
| --- | --- | --- | --- |
| P0 | 课堂录音与音频导入 | 开始、暂停、结束录音；导入已有音频；异常时尽量保留已录内容 | 支持常见音频格式，明确文件大小/时长上限；录音过程显示状态和时长 |
| P0 | 自动转写 | 带时间戳的文字记录，可跟随音频播放定位 | 先做好普通话；支持手动改错；保留原始转写版本 |
| P0 | 智能纪要 | 一句话概览、按主题分段、核心概念/结论、例子、课后任务与疑问 | 只根据本节录音生成；无法确定的内容标注“待核对” |
| P0 | 纪要与原文互跳 | 点击纪要条目，跳到对应转写句和音频时间点 | 输出带时间范围的依据，不只给整节课链接 |
| P0 | 课程/课次管理 | 按课程、日期和标题整理录音、转写、纪要 | 新建/改名/删除课程与课次；删除前确认 |
| P0 | 站内检索 | 找到某个术语出现在哪节课、哪段录音 | 先支持课程名、标题、转写正文和纪要关键词 |
| P0 | 数据导出 | 带走转写和纪要，避免资料被锁在产品里 | 至少支持 Markdown/TXT；音频保留原文件下载能力 |
| P1 | 课前资料关联 | 上传课件、讲义或照片，辅助识别术语和上下文 | 用户能区分“课堂原话”和“资料补充” |
| P1 | 录音时打点/记疑问 | 快速标记“重点”“没听懂”，课后直接回到该处 | 以最少操作完成，不干扰听课 |
| P1 | 基于课程资料问答 | 问“老师怎样解释这个概念”，回答引用课次与时间点 | 找不到依据时明确说不知道，不编造课堂内容 |
| P1 | 复习材料生成 | 从课堂内容生成知识点卡片、测验题和待复习清单 | 答案附来源；允许学生编辑 |
| P1 | 跨课次脉络 | 查看一个概念在不同课次如何推进 | 先基于手动选定的课程和课次 |
| P2 | 多人协作 | 与同学共享某节课的资料、批注和纠错 | 需有清晰的授权与撤销机制 |
| P2 | 个性化学习提醒 | 根据疑问、错题和复习进度提醒回顾 | 先验证学生是否真的需要提醒 |
| P2 | 多语种/说话人识别 | 适配双语授课和课堂讨论 | 根据真实样本验证准确率后再扩展 |

这些扩展功能有成熟的用户价值参考：NotebookLM 官方介绍了带来源引用的问答、学习指南、闪卡与测验等学习形式。ClassAgent 应把“课堂音频时间点可回溯”作为自己的核心体验，而不是仅复制通用摘要功能。参考：[NotebookLM 入门介绍](https://blog.google/innovation-and-ai/products/notebooklm-beginner-tips/)、[NotebookLM 学生功能](https://blog.google/innovation-and-ai/models-and-research/google-labs/notebooklm-student-features/)。

## 4. 首版建议（MVP）

建议先做 Web 端的个人资料库，录音可以从浏览器开始，也允许上传手机录好的文件。首版只覆盖一条完整闭环：

1. 用户创建课程和课次，开始录音或上传音频。
2. 系统保存音频并显示处理状态（待转写、转写中、生成纪要、完成、失败）。失败可重试，不丢失原音频。
3. 生成按时间分段的转写；用户可修改文字。
4. 生成结构化纪要：概览、主题脉络、关键概念、例题/案例、课后任务、待核对问题。
5. 每项纪要都能跳到相关原文和音频；用户可编辑纪要。
6. 用户按课程查看历史课次、搜索内容并导出。

**首版完成标准**：拿一段真实课堂录音，从导入到可编辑的转写和纪要能走通；纪要中的主要要点能回溯到音频；处理失败时保留音频并说明原因；删除和导出均可用。质量验证应使用不同教室噪声、语速和专业词汇的样本，由人工核对转写与纪要的遗漏和误述。

## 5. 交互与数据设计要点

- **核心对象**：课程（名称、学期等）→ 课次（日期、标题、状态）→ 音频 → 转写片段（起止时间、文本）→ 纪要条目（类型、文本、来源片段）。
- **可追溯性**：纪要引用转写片段的 ID 和音频时间区间。转写被修改后，应提示用户旧纪要可能需要重新生成。
- **可编辑性**：AI 结果是草稿；保存人工修改，避免重新生成时无提示覆盖。
- **长音频处理**：分段上传/处理、进度和失败重试需要从首版流程考虑。不要假定整节课能一次同步完成。
- **搜索范围**：首版用关键词即可；语义检索等到课程资料变多后再评估。
- **权限与隐私**：录音前提示用户确认已遵守课堂、学校及当地适用要求；默认私有；提供删除录音与派生内容、导出数据的能力。具体合规要求应在目标地区确定后核实。
- **成本控制**：记录每节课的音频时长、转写与模型调用成本；限制重复生成，先验证单位课次成本再决定免费额度。

## 6. 建议的实施顺序

| 阶段 | 交付物 | 验证重点 |
| --- | --- | --- |
| 0：需求验证 | 访谈数位目标学生，收集经许可的真实课堂样本，画出页面流程 | 最常见的课后任务是什么；录音质量是否足够 |
| 1：核心链路 | 课程/课次、录音或上传、音频保存、转写、纪要、来源跳转 | 完整跑通一节课，核对时间戳和内容准确性 |
| 2：资料管理 | 编辑、搜索、导出、失败重试、删除 | 多节课持续使用时是否找得到资料 |
| 3：学习 Agent | 带引用的问答、疑问整理、复习卡片、跨课次串联 | 是否比阅读普通纪要更能帮助复习 |

## 7. 需要尽早确定的问题

1. 优先做浏览器录音、移动端录音，还是“手机录音后上传”？这决定首版体验和技术方案。
2. 用户群以中文授课为主吗？是否必须处理英语、方言、多人讨论和板书？
3. 首版是否需要账号与云端同步，还是先做本地单机原型？
4. 音频允许上传到第三方语音识别/大模型服务吗？是否有本地处理要求？
5. 一节课常见时长、可接受的出结果时间、预计存储规模和预算是多少？

在这些问题确定前，先不锁定前后端框架或模型供应商；可以用少量真实样本比较转写质量、纪要忠实度、处理时延和成本，再定技术选型。
