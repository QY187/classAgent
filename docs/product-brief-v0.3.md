# ClassAgent 产品初版报告 v0.3

日期：2026-09-28
状态：产品构想；以下均为建议范围，尚未实现。本文用于讨论产品方向和首版范围，不等同于已确定的开发排期。

## 1. 产品定位

ClassAgent 面向需要课后回顾的学生，把课堂录音变成**可核对、可管理、可用于复习**的学习资料。它不只生成一段摘要：每个关键结论都应能定位到文字记录和对应音频，方便检查转写或 AI 理解是否准确。

### 已明确的核心需求

1. 支持上课时录音，也支持课后直接上传已有音频。
2. Agent 自动生成**带时间戳、区分说话人**的文字记录，以及类似飞书智能纪要的**完整课堂报告**。
3. 录音、文字记录、报告能按课程和课次持续管理。
4. 用户能针对一门课提问，回答综合该课程的多节课内容，并标明依据。

这里的“区分说话人”首先是识别“说话人 1 / 说话人 2”及发言区间；系统不能仅凭音频可靠获知真实姓名。用户可手动把某位说话人命名为“老师”“同学 A”等，并纠正误分段。

一节课的主要流程：创建课程与课次 → 录音（或导入已有音频）→ 自动转写 → 生成智能纪要 → 人工校订 → 按课程归档、搜索和复习。

## 2. 目标用户与主要场景

首要用户是大学生、自学课程学习者。典型场景包括：

- 上课时专注听讲，不必一边抄写所有内容；课后快速了解本节讲了什么。
- 缺席或听不清某一段时，按主题找到原文并回听。
- 考前把同一课程的多节课串起来复习，找出概念、例题和待解决问题。

首版先服务**个人使用**；班级协作、教师端和机构管理暂不进入首版。

### 三个优先解决的任务

| 任务 | 用户现在的困难 | 希望完成的结果 |
| --- | --- | --- |
| 课后十分钟回顾 | 一整节录音太长，完整重听成本高 | 先读到按讲课顺序整理的内容，再只回听关键片段 |
| 找到某个细节 | 记得老师讲过，却不知道在第几节、第几分钟 | 搜索术语后直接跳到相关原话和音频 |
| 考前复习 | 多节课的笔记分散，重点和疑问没有串起来 | 按课程整理概念、例题与未解决问题，形成复习清单 |

产品价值应以“用户找回并理解课堂信息所花的时间”衡量，而不只看生成了多少文字。

## 3. 功能建议与优先级

| 优先级 | 功能 | 用户能得到什么 | 首版边界 |
| --- | --- | --- | --- |
| P0 | 课堂录音与音频导入 | 开始、暂停、结束录音；导入已有音频；异常时尽量保留已录内容 | 支持常见音频格式，明确文件大小/时长上限；录音过程显示状态和时长 |
| P0 | 自动转写与说话人区分 | 带时间戳的“谁在什么时候说了什么”，可跟随音频播放定位 | 先做好普通话；默认说话人编号，可手动命名和纠错；保留原始转写版本 |
| P0 | 智能纪要报告 | 生成可阅读的整篇课堂报告，含概览、章节脉络、概念、例子、作业和疑问 | 只根据本节录音生成；无法确定的内容标注“待核对” |
| P0 | 纪要与原文互跳 | 点击纪要条目，跳到对应转写句和音频时间点 | 输出带时间范围的依据，不只给整节课链接 |
| P0 | 课程/课次管理 | 按课程、日期和标题整理录音、转写、纪要 | 新建/改名/删除课程与课次；删除前确认 |
| P0 | 站内检索 | 找到某个术语出现在哪节课、哪段录音 | 先支持课程名、标题、转写正文和纪要关键词 |
| P0 | 课程级问答 | 向一门课提问，综合多节课回答并引用课次、原文与时间点 | 仅检索选定课程；资料没有答案时明确说明；首版以转写和纪要为知识源 |
| P0 | 数据导出 | 带走转写和纪要，避免资料被锁在产品里 | 至少支持 Markdown/TXT；音频保留原文件下载能力 |
| P1 | 课前资料关联 | 上传课件、讲义或照片，辅助识别术语和上下文 | 用户能区分“课堂原话”和“资料补充” |
| P1 | 录音时打点/记疑问 | 快速标记“重点”“没听懂”，课后直接回到该处 | 以最少操作完成，不干扰听课 |
| P1 | 复习材料生成 | 从课堂内容生成知识点卡片、测验题和待复习清单 | 答案附来源；允许学生编辑 |
| P1 | 跨课次脉络 | 查看一个概念在不同课次如何推进 | 先基于手动选定的课程和课次 |
| P2 | 多人协作 | 与同学共享某节课的资料、批注和纠错 | 需有清晰的授权与撤销机制 |
| P2 | 个性化学习提醒 | 根据疑问、错题和复习进度提醒回顾 | 先验证学生是否真的需要提醒 |
| P2 | 多语种与更复杂的多人讨论 | 适配双语授课、方言和频繁插话 | 根据真实样本验证准确率后再扩展 |

这些扩展功能有成熟的用户价值参考：飞书官方介绍了妙记的逐字稿、章节纪要、待办和问答；NotebookLM 官方介绍了带来源引用的问答、学习指南、闪卡与测验。ClassAgent 应把“按课程持续积累、课堂音频时间点可回溯”作为自己的核心体验。参考：[飞书妙记](https://www.feishu.cn/content/article/7594772423082396858)、[NotebookLM 入门介绍](https://blog.google/innovation-and-ai/products/notebooklm-beginner-tips/)、[NotebookLM 学生功能](https://blog.google/innovation-and-ai/models-and-research/google-labs/notebooklm-student-features/)。

## 4. 首版建议（MVP）

建议先做 Web 端的个人资料库，录音可以从浏览器开始，也允许上传手机录好的文件。首版只覆盖一条完整闭环：

1. 用户创建课程和课次，开始录音或上传音频。
2. 系统保存音频并显示处理状态（待转写、转写中、生成纪要、完成、失败）。失败可重试，不丢失原音频。
3. 生成按时间和说话人分段的转写；用户可修改文字、重命名说话人。
4. 生成完整的结构化课堂报告：概览、主题脉络、关键概念、例题/案例、课后任务、待核对问题。
5. 每项纪要都能跳到相关原文和音频；用户可编辑纪要。
6. 用户按课程查看历史课次、搜索内容并导出。
7. 用户在课程范围内提问，收到带课次和音频时间点引用的回答。

**首版完成标准**：拿一段真实课堂录音，从导入到可编辑的分人转写和报告能走通；报告的主要要点能回溯到音频；同一门课至少有两节课时，问答能检索并引用正确课次；处理失败时保留音频并说明原因；删除和导出均可用。质量验证应使用不同教室噪声、语速和专业词汇的样本，由人工核对说话人分段、转写与报告的遗漏和误述。

## 5. 关键页面与具体操作

| 页面 | 核心内容 | 主要操作 |
| --- | --- | --- |
| 课程列表 | 课程名称、学期、课次数、最近更新 | 新建、改名、进入、删除课程 |
| 课程详情 | 按时间排序的课次、处理状态、最近重点 | 新建课次、搜索本课程、筛选待处理课次 |
| 录音/上传页 | 录音时长、输入设备与权限状态、上传进度 | 开始/暂停/结束录音、选择文件、录音时打点（P1） |
| 课次详情 | 音频播放器、智能纪要报告、文字记录并列呈现 | 点击纪要跳转、编辑文字与说话人、重新生成、导出、删除 |
| 全局搜索 | 搜索框、结果课次、命中片段和时间点 | 按课程筛选、跳到原文并回听 |
| 课程问答 | 提问输入框、回答、引用的课次与原文片段 | 追问、打开引用、限定课次范围 |

课次详情是核心页面。建议默认先显示“这节课讲了什么”的纪要，旁边保持可见的原文和播放器。用户点击“二分查找的时间复杂度”时，文字滚动到对应片段，音频定位到该片段起点；手动编辑后明确显示已保存。

### 一次完整操作示例

用户在“数据结构”课程创建“第 5 讲：二叉树”，上传 80 分钟录音。上传完成后，课次显示“转写中”；用户离开页面再回来仍能看到进度。完成后，首页给出本节的主题顺序、关键定义、老师演示的例题、布置的作业和待核对处。用户发现“前序遍历”被识别成“先序编历”，直接修正原文；系统提示纪要可能仍含旧措辞，可选择局部修订或重新生成。考前搜索“前序遍历”，可从结果直达这节课对应的讲解片段。

## 6. 核心功能的细化要求

### 6.1 录音与导入

- 录音开始前显示麦克风权限、当前输入设备和简短试听/音量反馈，避免录完才发现没有声音。
- 录音中显示计时和明显的录制状态；暂停与结束动作区分清楚。浏览器关闭、网络断开等情况下，应尽可能保存已录片段并提示恢复方式。
- 上传时展示文件名、时长、大小和进度；重复上传同一文件时提醒用户，但允许明确选择继续。
- 音频先保存成功，再触发后续 AI 处理。转写失败不能导致原音频丢失。
- 首版音频格式、最长时长和大小限制应在技术验证后确定，并在上传前明确告知用户。

### 6.2 文字记录

- 每段至少保存开始时间、结束时间和文本；点击文字能跳转音频，播放时可高亮当前段。
- 每段关联说话人编号；统一修改某位说话人的名称时，相关片段一起更新。允许把误判的单段改给另一位说话人。
- 保留自然段和基本标点，提供段落级编辑。用户编辑的内容与机器原文应可区分或恢复。
- 专业词汇、英文缩写和人名容易出错；首版先支持人工纠错，后续再考虑课程词表。
- 不确定的识别结果不要伪装成确定原话。可以标出低置信度片段或提示“请回听核对”，但是否能拿到可靠置信度取决于转写服务。

### 6.3 智能纪要

报告采用可阅读的段落和小标题，不能只是关键词列表。建议固定以下模板，减少每次输出样式飘忽：

1. **一句话概览**：这节课的主题与推进关系。
2. **按讲课顺序的主题**：每段 2–4 条要点，标出大致时间范围。
3. **关键概念与定义**：尽量保持老师的语境，不把补充常识当作课堂原话。
4. **例题/案例**：题目、讲解思路、结论；录音缺失时不补造题目。
5. **作业与下节预告**：仅在录音中确实提到时显示。
6. **待核对/没听清**：语音模糊、矛盾或缺少上下文的部分。

示意条目（仅演示格式，非真实课堂内容）：

> **主题：二叉树遍历**（约 24:10–39:20）
>
> 老师先区分前序、中序、后序遍历，再用一棵三层二叉树演示访问顺序。
>
> **例题**：给定树结构，求三种遍历序列。
>
> **来源**：转写第 68–94 段；点击后跳到 24:10。
>
> **待核对**：例题中一个节点名称听不清。

生成约束：纪要只能概括有音频或用户补充资料支撑的内容；每个实质性要点关联一个或多个来源片段；无法确认的作业、日期、公式等不可猜测。若未来引入课件作为来源，应标明“课堂录音”还是“课件内容”。

### 6.4 课程级问答与 RAG

- 用户先选定一门课程，再输入问题；默认在该课程的全部已完成课次中检索，也可限定某几节课。
- 系统先找到相关转写片段和报告内容，再据此生成回答。每个关键结论附课次、时间点和可点击的原文；多个课次说法不一致时指出差异。
- 找不到可靠依据时回答“目前课程资料中没有找到”，可建议用户换问法，但不能把模型常识冒充老师讲过的话。
- 支持基于当前答案追问；每次追问仍需检索课程材料，不能只依赖聊天历史。
- 首版用带时间戳的转写片段作为主要检索单位；是否需要向量检索、混合检索和重排，取决于实际课程数据量与查询效果。RAG 是可能采用的实现方案，不应让用户看到技术术语。

示例：问“老师在第几节讲过二叉树的前序遍历？和中序有什么区别？”回答应列出对应课次、两种遍历的课堂解释，并能点击引用回到各自的音频位置。

### 6.5 管理、检索与导出

- 课程和课次支持改名、调整归属、按日期排序。空课程也可以保留，删除课程时明确会影响哪些课次。
- 搜索结果至少显示课程、课次、命中上下文和时间点；关键词同时检索转写与纪要。
- 导出纪要和转写时保留标题、日期、时间戳与来源提示；音频单独下载。导出的内容应可在产品外阅读。
- 用户删除课次时应说明音频、转写、纪要会一起删除；若未来加入云端备份，需另行设计删除范围和恢复期。

## 7. 异常情况与验收清单

| 情况 | 用户应看到的结果 | 验收方式 |
| --- | --- | --- |
| 麦克风权限被拒绝 | 明确提示如何开启权限，并提供上传音频入口 | 禁止麦克风后仍可进入上传流程 |
| 录音意外中断 | 已保存片段可找回，状态标明不完整 | 录制中刷新/关闭页面后核对可恢复内容；具体能力需按浏览器验证 |
| 上传网络中断 | 进度停止并可重试，不出现“已完成”假状态 | 模拟断网后恢复上传或重新上传 |
| 转写/生成纪要失败 | 展示失败阶段和重试按钮，原音频保留 | 注入服务失败并确认音频仍可播放 |
| 音频中长时间静音或噪声 | 纪要不编造内容，提示信息不足 | 用静音与噪声样本人工检查 |
| 转写被用户修改 | 已生成纪要提示可能过期；重新生成不静默覆盖人工改动 | 修改关键术语后检查提示与版本 |
| 纪要声称有作业但录音没有 | 视为严重错误，必须回到来源核对 | 抽样逐条比对纪要和音频 |
| 两人同时说话或环境噪声大 | 说话人标记允许为“未确定”，用户可手动修正 | 用多人插话样本验证，不强行赋予真实姓名 |
| 问答所需内容不在本课程 | 明确表示资料不足，不引用其他课程内容 | 用跨课程问题验证检索隔离 |

## 8. 交互与数据设计要点

- **核心对象**：课程（名称、学期等）→ 课次（日期、标题、状态）→ 音频 → 转写片段（起止时间、文本）→ 纪要条目（类型、文本、来源片段）。
- **可追溯性**：纪要引用转写片段的 ID 和音频时间区间。转写被修改后，应提示用户旧纪要可能需要重新生成。
- **可编辑性**：AI 结果是草稿；保存人工修改，避免重新生成时无提示覆盖。
- **长音频处理**：分段上传/处理、进度和失败重试需要从首版流程考虑。不要假定整节课能一次同步完成。
- **搜索范围**：首版用关键词即可；语义检索等到课程资料变多后再评估。
- **权限与隐私**：录音前提示用户确认已遵守课堂、学校及当地适用要求；默认私有；提供删除录音与派生内容、导出数据的能力。具体合规要求应在目标地区确定后核实。
- **成本控制**：记录每节课的音频时长、转写与模型调用成本；限制重复生成，先验证单位课次成本再决定免费额度。

### 数据关系草图

```text
用户
 └─ 课程
     └─ 课次
         ├─ 音频文件
         ├─ 说话人（编号、用户命名）
         ├─ 转写版本 → 转写片段（开始/结束时间、说话人、文本）
         ├─ 纪要版本 → 纪要条目 → 引用的转写片段
         └─ 用户标记/疑问（P1）
```

课次必须有稳定 ID，不能用标题当关联键。音频、转写和纪要分开存储，便于处理失败后单独重试，也便于保留人工修改和版本。生成纪要时记录其依据的转写版本；这样转写更新后才能准确提示“纪要可能过期”。

### 初步技术路径（待验证）

浏览器负责录音/上传与查看结果；服务端负责保存文件、排队执行转写和纪要任务、持久化课次数据。长音频处理采用异步任务，前端查询任务状态。转写结果需保留时间戳；纪要生成阶段让模型输出结构化条目及其引用片段，再做引用有效性检查。首版可以先使用成熟的语音识别和大模型服务，随后根据真实课堂样本、隐私要求和成本决定是否转向本地模型。这里是实现方向，不指定具体供应商。

课程问答需要把已完成课次的转写切成可检索片段，同时保存课程、课次、时间区间和版本信息。检索先严格限定课程，再从命中的片段生成回答并校验引用是否存在。转写更新后，相应索引应更新；课次删除后，对应检索内容也应删除。先用小样本验证关键词检索是否足够，再决定是否引入向量索引。

## 9. 评估指标与实施顺序

首版除了确认功能能运行，还需记录以下指标。具体目标值应在收集样本后设定，避免凭空承诺准确率：

- **录音可靠性**：有多少次录音最终得到可播放的完整文件；意外中断后保留了多少内容。
- **处理成功率与耗时**：上传、转写、纪要各阶段的成功率和每小时音频的处理时间。
- **转写质量**：在普通话、噪声、专业术语等不同样本上的人工纠错量。
- **纪要忠实度**：抽查要点是否有对应来源，是否遗漏关键结论，是否出现无依据内容。
- **说话人分段质量**：抽查讲话人切换位置与误分配片段，记录人工纠正量。
- **问答可信度**：抽查答案是否引用正确课程和时间点；无答案的问题是否会错误编造。
- **实际使用价值**：用户从打开课次到找到一个指定知识点所需时间；生成后是否会回看、搜索和编辑。
- **单位成本**：每小时音频对应的存储、转写和模型调用成本。

| 阶段 | 交付物 | 验证重点 |
| --- | --- | --- |
| 0：需求验证 | 访谈数位目标学生，收集经许可的真实课堂样本，画出页面流程 | 最常见的课后任务是什么；录音质量是否足够 |
| 1：单节课闭环 | 课程/课次、录音或上传、音频保存、分人转写、纪要报告、来源跳转 | 完整跑通一节课，核对时间戳、说话人和内容准确性 |
| 2：课程资料库 | 编辑、搜索、导出、失败重试、删除、带引用的课程问答 | 多节课持续使用时能否找到资料并回答有依据的问题 |
| 3：学习扩展 | 疑问整理、复习卡片、跨课次串联 | 是否比阅读普通纪要更能帮助复习 |

## 10. 需要尽早确定的问题

1. 优先做浏览器录音、移动端录音，还是“手机录音后上传”？这决定首版体验和技术方案。
2. 用户群以中文授课为主吗？是否必须处理英语、方言、多人讨论和板书？
3. 首版是否需要账号与云端同步，还是先做本地单机原型？
4. 音频允许上传到第三方语音识别/大模型服务吗？是否有本地处理要求？
5. 一节课常见时长、可接受的出结果时间、预计存储规模和预算是多少？

在这些问题确定前，先不锁定前后端框架或模型供应商；可以用少量真实样本比较转写质量、纪要忠实度、处理时延和成本，再定技术选型。
