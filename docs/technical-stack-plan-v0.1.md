# ClassAgent 技术栈方案 v0.1

日期：2026-09-28  
状态：首版技术方案，待用真实课堂样本验证  
适用范围：个人用户 Web 版 MVP

## 1. 方案目标

本方案服务于 ClassAgent 的首版闭环：

> 录音或上传音频 → 保存音频 → 异步转写 → 生成可回溯的智能纪要 → 编辑、搜索、导出 → 课程范围内问答

技术方案优先保证以下能力：

- 长音频可以异步处理，不阻塞网页请求。
- 原始音频、转写和纪要分别保存，任一处理阶段失败都可以重试。
- 纪要中的关键内容可以回到转写片段和音频时间点。
- 用户的人工修改不会被模型静默覆盖。
- 首版可以快速验证，后续能够替换语音识别和大模型服务。

## 2. 推荐技术栈

| 层次 | 首版选型 | 主要用途 |
| --- | --- | --- |
| Web 前端 | Next.js、React、TypeScript | 页面、路由、服务端渲染和前端类型检查 |
| UI | Tailwind CSS、shadcn/ui | 课程列表、播放器、编辑器和状态组件 |
| 浏览器录音 | MediaRecorder API | 录音、暂停、继续和录音片段上传 |
| 后端 API | Python、FastAPI、Pydantic | 用户、课程、课次、文件和 AI 任务接口 |
| 异步任务 | Celery 或 Dramatiq、Redis | 转码、转写、纪要、索引和重试任务 |
| 主数据库 | PostgreSQL | 业务数据、转写片段、纪要和版本关系 |
| 文件存储 | S3 兼容对象存储 | 原始音频、转码文件和导出文件 |
| 音频处理 | FFmpeg | 格式转换、时长提取、切片和音频规范化 |
| 首版搜索 | PostgreSQL Full-Text Search | 课程、标题、转写和纪要关键词搜索 |
| 后续语义搜索 | pgvector | 课程问答的向量检索，可在数据量增加后启用 |
| 语音识别 | 可替换的 ASR 服务官方 SDK | 转写、时间戳和说话人区分 |
| 大模型 | 可替换的 LLM 服务官方 SDK | 纪要、问答和复习材料生成 |
| 认证 | Auth.js、Supabase Auth 或同类服务 | 登录、会话和基础用户身份 |
| 本地开发 | Docker Compose | PostgreSQL、Redis、MinIO 等依赖服务 |
| 部署 | Docker 化部署、托管 PostgreSQL 和对象存储 | 首版上线和后续扩容 |
| 监控 | Sentry、结构化日志 | 前端异常、后端异常和任务失败追踪 |

首版采用单体后端加独立任务 Worker，不拆分微服务。这样可以降低部署和联调成本，同时保留异步处理能力。

## 3. 系统架构

```text
浏览器
  ├─ 录音/上传
  ├─ 课程与课次页面
  ├─ 音频播放器
  ├─ 转写和纪要编辑器
  └─ 搜索与课程问答
          │ HTTPS
          ▼
FastAPI 应用
  ├─ 认证与权限
  ├─ 课程/课次 API
  ├─ 音频上传签名 URL
  ├─ 处理状态 API
  ├─ 搜索 API
  └─ 问答 API
          │
          ├──────── PostgreSQL
          ├──────── Redis
          └──────── S3 兼容对象存储
                         │
                         ▼
                   Worker 任务
                    ├─ FFmpeg 转码/切片
                    ├─ ASR 转写
                    ├─ 纪要生成
                    ├─ 来源引用校验
                    └─ 搜索索引更新
```

浏览器不直接持有模型服务密钥。音频上传可以使用后端签发的短期签名 URL，上传完成后再由后端创建处理任务。

## 4. 后端与 AI 能力层

### 4.1 FastAPI 业务后端

FastAPI 负责稳定的业务边界，不把课程和文件管理逻辑放进模型框架。主要模块包括：

- `auth`：登录、会话和用户权限。
- `courses`：课程和课次的增删改查。
- `audio`：上传、文件元数据、下载和删除。
- `processing`：处理任务、状态、进度和重试。
- `transcripts`：转写版本、片段编辑和说话人管理。
- `summaries`：纪要版本、纪要条目和人工编辑。
- `search`：课程范围内的关键词搜索。
- `qa`：课程问答、引用和追问。
- `exports`：Markdown/TXT 导出。

### 4.2 AI 服务适配层

使用模型服务提供商的官方 SDK 调用 ASR、LLM 和 Embedding 服务，在应用内部统一封装接口：

```python
class SpeechToTextService:
    async def transcribe(self, audio_uri: str) -> TranscriptResult:
        ...

class SummaryService:
    async def generate(self, transcript: Transcript) -> SummaryResult:
        ...

class CourseQAService:
    async def answer(self, course_id: str, question: str) -> AnswerResult:
        ...
```

这样可以替换模型供应商，而不修改课程、课次和问答业务代码。首版不强制引入 LangChain 或 LlamaIndex；简单的“检索片段 → 生成回答 → 校验引用”流程先由业务代码实现，便于调试和保证引用正确。复杂 RAG 流程稳定后再评估引入编排框架。

### 4.3 结构化模型输出

纪要不直接依赖一段不可校验的 Markdown。模型应输出符合 Pydantic Schema 的结构化数据，包括：

- 概览
- 主题条目
- 关键概念
- 例题/案例
- 作业和下节预告
- 待核对内容
- 转写片段 ID 和音频起止时间

后端需要检查来源片段是否真实存在、是否属于当前课次、是否属于生成时使用的转写版本。检查失败的条目不能直接展示为可靠结论。

## 5. 音频处理流程

1. 前端检查麦克风权限、文件格式、文件大小和时长。
2. 后端创建课次和音频记录。
3. 音频上传到对象存储，成功后才创建处理任务。
4. Worker 使用 FFmpeg 提取时长并统一音频格式。
5. 长音频按服务要求切片，保留原始时间偏移。
6. 调用 ASR 服务生成带时间戳的转写和说话人区间。
7. 保存机器转写版本，生成可编辑的转写片段。
8. 调用 LLM 生成结构化纪要。
9. 校验纪要引用，并保存纪要版本。
10. 更新关键词搜索索引，课次状态改为完成。

每个步骤都写入 `processing_jobs`，保存当前阶段、进度、错误原因、重试次数和开始/结束时间。

## 6. 数据模型

核心关系如下：

```text
User
 └─ Course
     └─ Lesson
         ├─ AudioFile
         ├─ TranscriptVersion
         │   └─ TranscriptSegment
         ├─ SummaryVersion
         │   └─ SummaryItem
         │       └─ SummaryCitation → TranscriptSegment
         ├─ ProcessingJob
         └─ Bookmark/Question
```

关键设计：

- `lesson_id` 是课次稳定关联键，不能用标题作为关联键。
- `TranscriptSegment` 至少保存开始时间、结束时间、说话人、文本和原始文本。
- `SummaryVersion` 记录生成时使用的 `transcript_version_id`。
- 用户修改转写后，标记纪要为“可能过期”，不自动覆盖人工修改。
- 课次删除时，删除音频、转写、纪要、搜索索引和相关任务数据。
- 对象存储文件通过数据库元数据管理，不在业务表中保存临时下载链接。

## 7. 课程问答方案

首版采用限定课程范围的检索增强问答：

1. 用户选择一门课程。
2. 后端只检索该课程已完成课次的转写片段和纪要内容。
3. 首版使用 PostgreSQL 全文搜索；数据量增加后补充 pgvector。
4. 将命中片段、课次、时间点和版本信息传给 LLM。
5. LLM 输出回答和引用片段 ID。
6. 后端校验每个引用，返回可点击的课次、原文和音频时间点。

当检索不到可靠资料时，回答应明确说明课程资料中没有找到，不能使用模型常识冒充课堂内容。

## 8. 部署与环境

### 开发环境

- Docker Compose 默认启动 PostgreSQL、Redis、API 和 Worker。
- 生产环境接入 S3 兼容对象存储；本地验证可以使用挂载卷作为临时文件存储，业务接口保持不变。
- 前端和后端使用独立开发服务器。
- AI 服务密钥只放在服务端环境变量中。
- 使用 `.env.example` 记录配置项名称，不提交真实密钥。

### 测试环境

- 使用独立数据库和对象存储桶。
- 使用小型、经过授权的课堂样本。
- 对转写、纪要和问答服务使用可控的测试替身或固定样本。

### 生产环境

- 前端、API 和 Worker 分开部署，但共享同一代码仓库。
- PostgreSQL 使用托管服务并启用备份。
- 对象存储开启私有访问，使用短期签名 URL。
- Redis 用于任务队列，不作为唯一数据存储。
- 记录音频时长、模型调用次数、处理耗时和失败原因，用于成本控制。

## 9. 安全与隐私

- 默认课程、音频、转写和纪要为用户私有。
- 所有音频访问通过用户权限校验和短期签名 URL。
- 音频和派生内容支持一并删除。
- 录音前显示课堂录音和第三方处理提示。
- 日志中不得记录完整音频内容、完整转写或模型密钥。
- 生产环境使用 HTTPS，密钥通过部署平台的安全配置注入。
- 后续加入分享功能时，再设计查看、编辑、下载和撤销权限。

## 10. 分阶段实施

### 阶段 1：单节课闭环

- Next.js 页面和基础播放器
- FastAPI 课程、课次和音频 API
- PostgreSQL、Redis、对象存储
- 音频上传和处理状态
- ASR 转写和说话人区分
- 结构化纪要生成
- 纪要到原文和音频的跳转
- 基础编辑和失败重试

### 阶段 2：课程资料库

- 登录和用户隔离
- 课程列表和课次管理
- 转写、纪要搜索
- Markdown/TXT 导出
- 版本管理和过期提示
- 课程范围问答
- 删除和数据清理

### 阶段 3：学习扩展

- pgvector 和混合检索
- 重点/疑问标记
- 复习卡片和测验题
- 跨课次知识整理
- 课件和讲义关联
- 多人共享和权限管理

## 11. 暂不采用的方案

首版暂不采用以下方案：

- Kubernetes 和微服务集群
- 独立向量数据库
- 自建 GPU 模型推理集群
- 复杂 Agent 框架
- 首版就支持多语种、方言和复杂多人讨论

原因是当前最大的验证风险是转写质量、长音频可靠性、纪要来源准确性和课程问答可信度。先用可替换的外部 AI 服务和简单可观测的后端流程验证产品，再根据真实数据决定是否自建模型或扩展基础设施。

## 12. 首版技术验收标准

- 一段真实课堂录音可以完成上传、转写、纪要和查看。
- 转写片段包含可用的开始时间、结束时间和说话人信息。
- 每个主要纪要条目都能回到有效转写片段和音频时间点。
- 处理失败后可以重试，原始音频仍可播放和下载。
- 修改转写后，系统能提示纪要可能过期。
- 同一课程的多节课可以搜索和问答。
- 问答引用只能来自当前课程，并能点击回到来源。
- 用户可以导出和删除自己的资料。
- 能记录处理耗时、失败率和每小时音频的 AI 调用成本。

## 13. 待确定事项

以下事项需要用真实样本和预算进一步确定：

1. 首版使用哪一家 ASR 和 LLM 服务。
2. 是否必须支持浏览器直接录音，还是先只支持上传。
3. 是否需要首版登录和多设备同步。
4. 一节课的最大时长、文件大小和可接受处理时间。
5. 音频是否允许上传第三方服务，是否需要本地部署模型。
6. 预计用户量、存储规模和每小时音频成本上限。
