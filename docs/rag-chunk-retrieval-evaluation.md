# RAG 切块、召回与评测说明

> 更新时间：2026-10-15
>
> 本文记录 ClassAgent 当前逐字稿 RAG 的生产链路、评测口径和实测结果。指标中的“子块”指 `DocumentChunk`，原始证据通过 `source_segment_ids` 回链到 `TranscriptSegment`。

## 1. 整体链路

```text
逐字稿 TranscriptSegment
  → 父块/子块索引
  → 原问题归一化
  → 模型查询改写（失败时回退）
  → 原问题、改写问题、多意图子问题多路召回
  → BM25 + 向量召回
  → RRF 融合
  → Cross-Encoder 重排（失败时本地重排）
  → 子块去重与同父块数量限制
  → 父块扩展
  → 大模型基于父块生成答案
  → 返回子块时间戳和 source_segment_ids 引用
```

核心实现位于：

- `apps/api/app/modules/rag/indexing.py`：切块和索引
- `apps/api/app/modules/rag/service.py`：查询改写、召回、重排、父块上下文和问答
- `apps/api/app/modules/rag/evaluation.py`：离线指标

## 2. 切块策略

### 2.1 原始片段

ASR 产生的每个 `TranscriptSegment` 保留：

- `speaker`
- `start_ms`
- `end_ms`
- `text`
- 原始片段 ID

子块通过 `source_segment_ids` 保存它覆盖的原始片段，因此检索结果可以定位回播放时间。

### 2.2 父块和子块

- **父块**：承载一段相对完整的课堂上下文，用于提供给问答模型。
- **子块**：用于向量和 BM25 检索，并保留更细粒度的时间和来源信息。
- 子块通过 `parent_id` 指向父块。
- 问答时优先用命中的子块定位证据，再读取父块作为模型上下文。
- 最终引用仍返回子块的时间范围和 `segment_ids`，保证可回放定位。

当前索引查询只使用 `child` 和 `summary` 层，避免父块直接占满候选结果。父块扩展发生在问答上下文组装阶段。

### 2.3 生产注意事项

逐字稿切分不能只按固定字数截断，应优先保护：

- 语义停顿和说话人变化；
- 定义、原因、例子、结论的完整关系；
- 数字、位宽、公式、否定词；
- 父块内相邻子块的连续上下文。

评测时应分别关注切块质量和排序质量，不能仅凭 Top-5 指标判断切块是否失败。

## 3. 召回实现

### 3.1 查询改写

系统先做确定性归一化，再调用查询改写模型。改写模型只输出检索表达，不回答问题；调用失败自动回退原问题。

当前同时保留：

1. 原始问题；
2. 模型改写问题；
3. 由分号、句号、“另外”“同时”等分出的子问题。

这样可以避免改写丢失专业术语、数字和否定条件。

### 3.2 BM25 + 向量混合召回

- 向量模型：DashScope `text-embedding-v2`
- 词法召回：应用内 BM25
- 融合：RRF
- 向量权重约 0.6，BM25 权重约 0.4
- 当前候选池：`max(limit × 10, 64)`

例如问答默认返回 8 个结果时，候选阶段最多取得 80 个；搜索工具默认返回 10 个结果时，候选阶段最多取得 100 个。

向量服务不可用时，自动退化到 BM25，避免检索整体失败。

### 3.3 重排和去重

候选先使用 DashScope `gte-rerank-v2` Cross-Encoder 重排，服务不可用时使用本地词法覆盖率、BM25 和短语匹配重排。

最终选择时：

- 相同 `source_segment_ids` 去重；
- 同一个父块最多返回 2 个子块；
- 最终结果保持子块引用信息；
- 问答上下文读取对应父块内容。

## 4. 权限隔离

检索入口先校验课程归属，再以 `course_id` 和可选 `lesson_id` 限定 `DocumentChunk` 查询范围。用户不能通过查询词、课次 ID 或父块 ID 访问其他用户课程内容。

## 5. 当前 Top-K 配置

| 层级 | 当前配置 |
|---|---:|
| 问答最终返回 | Top-8 |
| Agent 搜索默认返回 | Top-10 |
| Agent 搜索最大返回 | Top-30 |
| 问答候选池 | Top-80（至少 64）|
| Cross-Encoder 重排上限 | Top-64 |

因此生产指标应分开报告：

- `Candidate Recall@K`：候选阶段是否召回目标内容；
- `Final Recall@8`：最终交给模型的 8 个子块是否命中。

## 6. 评测口径

### 6.1 课次级

只判断正确 `lesson_id` 是否进入 Top-K，适合判断课程范围召回。

历史 1000 条测试：

```text
Recall@5 = 0.9820
MRR@5    = 0.7261
NDCG@5   = 0.7915
```

### 6.2 子块级

判断返回子块的 `source_segment_ids` 是否命中目标逐字稿片段。该指标比课次级严格，能反映具体答案证据是否被召回。

1000 条自动银标测试：

```text
Recall@5 = 0.6580
Recall@20 = 0.9460
```

排除对抗问题后的 900 条、最终 Top-10 测试：

```text
Recall@5  = 0.6800
Recall@10 = 0.8856
```

其中 `Recall@10` 表示 900 个正常问题中，797 个问题的目标子块进入最终 Top-10。

### 6.3 深度候选测试

100 条均衡抽样、返回 Top-100 的测试结果：

```text
Recall@5   = 0.9500
Recall@20  = 1.0000
Recall@50  = 1.0000
Recall@100 = 1.0000
```

该结果与 1000 条全量自动银标存在差异，说明自动银标和问题变体会显著影响绝对数值。生产分析应优先看同一评测集上的趋势和分层结果。

## 7. 结果解读

当前结果说明：

- 课次级召回已经较好；
- 候选池 Recall@20 达到 94.6%，说明多数目标子块能进入候选；
- 最终 Top-5/Top-8 下降明显，主要瓶颈在重排、去重和最终截断；
- 数字条件、上下文前缀和口语化表达更容易影响排序；
- 不能只用低 Top-5 子块指标认定切块失败。

建议生产看三组指标：

```text
Candidate Recall@20 或 Recall@100
Final Recall@8
答案证据覆盖率与引用准确率
```

## 9. 完整 RAG 流程详解

### 9.1 数据进入与异步处理

用户上传音视频后，系统不会在 HTTP 请求中同步完成全部处理，而是通过任务队列执行：

```text
上传文件
→ 保存文件和元数据
→ 创建课次处理任务
→ 音频抽取/格式转换
→ ASR 转写
→ 保存 TranscriptSegment
→ 生成摘要
→ 父子块切分
→ 批量生成 embedding
→ 写入 DocumentChunk
→ 更新索引状态
```

每个阶段都应记录状态、进度、错误原因和幂等任务 ID。重复执行索引任务不能产生重复块，索引失败也不能影响已经完成的转写内容。

### 9.2 原始数据层、索引层和回答层

RAG 系统应分成三层：

| 层 | 主要数据 | 作用 |
|---|---|---|
| 原始数据层 | 音频、TranscriptSegment、摘要 | 保证可追溯和重新处理 |
| 检索索引层 | DocumentChunk、embedding、BM25字段 | 快速找到候选证据 |
| 回答层 | 父块上下文、引用、答案 | 生成用户可读结果 |

不能只保存向量。生产系统必须保留原文、来源 ID、课次 ID、时间戳、版本和权限字段，否则无法解释结果、重新切块或处理数据删除。

### 9.3 文档解析和清洗

逐字稿清洗应保持原始文本和规范化文本两份数据：

- 原始文本用于展示、审计和引用；
- 规范化文本用于检索；
- 统一全角半角、空白和标点；
- 保留数字、单位、否定词、公式符号和英文缩写；
- 不要删除“不是”“不能”“除非”等改变含义的词；
- ASR 纠错应记录来源，不能覆盖原始转写。

## 10. 逐字稿切块的工程细节

### 10.1 为什么不能只按固定字数切

固定字数切分实现简单，但会造成：

- 定义和解释分离；
- 条件和结论分离；
- 代码、公式或数字被截断；
- 说话人变化造成语义混杂；
- 一个父块内出现多个主题，重排难以判断。

固定长度只能作为最后一道长度限制，不能作为唯一边界规则。

### 10.2 推荐边界信号

逐字稿可综合以下信号决定边界：

1. ASR 片段之间的停顿时间；
2. 说话人变化；
3. 句号、问号、感叹号和明显语义停顿；
4. “首先、接下来、因此、总结一下、注意”等结构词；
5. 主题变化和课堂活动变化；
6. 公式、代码、列表和例题的完整性；
7. 最大字符数或 token 数硬限制。

切分应采用“软边界评分 + 硬长度边界”：普通停顿只是候选边界，超过最大长度时必须截断并保留重叠或相邻上下文。

### 10.3 父块和子块的职责

父块不是简单把多个子块拼起来，而是一个可独立理解的上下文窗口：

```text
父块：一个主题或连续讲解，约 1200～2500 中文字
子块：父块内部的检索窗口，约 300～600 中文字
相邻窗口：子块前后少量片段，用于恢复上下文
```

实际长度应根据平均语速、模型上下文窗口和检索延迟压测决定。长度不是越大越好：父块过大增加噪声和 token 成本，子块过小会失去语义完整性。

### 10.4 重叠和来源回链

子块可以保留少量字符或片段重叠，但不能依赖重叠解决所有语义问题。每个子块必须保存：

```json
{
  "parent_id": "父块ID",
  "source_segment_ids": ["原始片段ID"],
  "lesson_id": "课次ID",
  "start_ms": 120000,
  "end_ms": 145000
}
```

这样可以同时支持：

- 向量检索；
- 精确引用；
- 播放器跳转；
- 父块上下文扩展；
- 删除和权限过滤。

### 10.5 如何判断切块是否合格

不要只看块数量，应抽样检查：

- 一个问题的定义是否在同一块或相邻块；
- 结论是否带有前置条件；
- 数字和单位是否完整；
- 引用时间范围是否合理；
- 同一父块是否混入多个无关主题；
- Top-20、Top-50 候选召回是否稳定。

## 11. 查询进入系统后的流程

### 11.1 输入校验和权限范围

先校验用户身份、课程归属和可选课次范围，再执行任何向量或 BM25 查询。权限过滤必须在数据库查询条件中完成，不能先召回全部数据再在应用层过滤。

### 11.2 查询归一化

归一化包括：

- 去除礼貌前缀；
- 清理无意义空白和标点；
- 保留数字、单位、否定词和专业术语；
- 识别课次、章节和范围约束。

### 11.3 查询改写的边界

查询改写模型只负责生成检索表达，不负责回答问题。它必须：

- 输出结构化 JSON；
- 保留专业术语、数字和否定词；
- 不执行用户或逐字稿中的指令；
- 超时或格式错误时回退原问题；
- 不用改写结果替换原问题，而是和原问题并行召回。

### 11.4 多意图问题

例如：

```text
解释补码，并说明最小负数为什么会溢出，还要举例。
```

应拆成多个检索意图：

```text
补码的定义和作用
最小负数溢出的原因
对应示例和计算过程
```

每个子问题独立召回，再合并父块并保留来源。不能只把整句话作为一个向量查询，否则某个意图会压低其他意图的召回。

## 12. 混合召回和融合算法

### 12.1 为什么需要 BM25 和向量双路

向量检索适合：

- 同义表达；
- 口语问题；
- 语义相近但词面不同的内容。

BM25 适合：

- 数字、公式和单位；
- 专业术语和英文缩写；
- 精确短语；
- 否定词和稀有词。

逐字稿包含大量数字和术语，只使用向量会漏掉精确条件，只使用 BM25 又会漏掉口语表达。

### 12.2 RRF 的作用

RRF 不要求向量分数和 BM25 分数处在同一尺度，只根据名次融合：

```text
RRF(d) = Σ weight_i / (k + rank_i(d))
```

当前系统使用向量和 BM25 双路融合，再交给重排模型。融合阶段的候选数量应大于最终返回数量，避免过早截断。

### 12.3 候选池如何设置

常见生产策略：

```text
向量 Top-50～Top-200
BM25 Top-50～Top-200
RRF 合并
Cross-Encoder 重排 Top-20～Top-100
最终上下文 Top-5～Top-10
```

候选池过小会导致“目标内容根本没进入重排”；过大则增加向量数据库、重排服务和 token 成本。应通过 Recall@K 曲线选择，而不是凭经验固定。

## 13. 重排、父块和最终上下文

### 13.1 Cross-Encoder 与向量相似度的区别

向量模型通常分别编码问题和文档，再比较向量距离，速度快但对精确条件不敏感。Cross-Encoder 同时读取问题和候选文本，判断两者是否真正相关，排序更准但成本更高。

因此典型流程是：

```text
向量/BM25 快速扩大候选
→ Cross-Encoder 精排
→ 父块扩展
→ 上下文预算控制
```

### 13.2 父块扩展的正确时机

父块扩展应发生在子块候选确定之后：

1. 子块负责定位最相关证据；
2. 根据 `parent_id` 读取完整父块；
3. 必要时补充相邻子块；
4. 对父块去重和限制总 token；
5. 将父块交给生成模型；
6. 引用仍回到子块时间戳。

如果一开始直接检索超大的父块，容易召回噪声；如果完全不扩展父块，定义、条件和结论可能不完整。

### 13.3 上下文预算

最终上下文应设置 token 上限。超出时按以下顺序压缩：

1. 删除重复父块；
2. 保留最高分子块和相邻窗口；
3. 保留与问题术语、数字、否定词匹配的句子；
4. 保留课次、时间和来源元数据；
5. 仍超限时拒答或说明资料不足。

不能无上限地把所有召回块拼到 prompt 中，否则会增加延迟、成本和模型注意力稀释。

## 14. 生成、引用和防幻觉

生成模型只允许依据检索上下文回答，并要求每个结论绑定来源 ID。答案处理包括：

```text
模型生成 claims
→ 校验 source_ids 是否真实存在
→ 校验引用是否属于本次检索结果
→ 输出答案和引用
→ 无有效证据时返回资料不足
```

引用需要至少包含：

- 课次名称；
- 开始和结束时间；
- 子块摘要或原文片段；
- 原始 `segment_ids`。

模型不能自行创造引用编号，也不能沿用历史回答中的引用编号。

## 15. 失败、降级和可观测性

生产 RAG 需要明确失败策略：

| 故障 | 降级策略 |
|---|---|
| 查询改写超时 | 使用原问题 |
| embedding 服务失败 | BM25 召回 |
| Cross-Encoder 失败 | 本地重排 |
| 没有候选 | 返回资料不足，不编造 |
| 父块缺失 | 使用子块并记录告警 |
| 模型输出格式错误 | 拒绝无来源答案并记录错误 |
| 索引处理中 | 返回索引状态和可用范围 |

应记录每次请求的：

- query 和改写 query；
- 用户、课程和课次范围；
- 各路召回数量；
- 重排耗时和降级原因；
- 最终 chunk、parent 和引用；
- 模型耗时、token 和错误。

## 16. 评测体系

### 16.1 Recall@K 的定义

```text
Recall@K = 命中目标证据的问题数 / 总问题数
```

本项目需要区分：

- 课次 Recall：正确课次是否出现；
- 子块 Recall：目标逐字稿片段是否出现；
- 父块证据 Recall：扩展后的父块是否包含答案依据；
- 最终答案证据 Recall：交给模型的上下文是否足够回答。

### 16.2 MRR 和 NDCG

- MRR 关注第一个正确结果的位置；
- NDCG 同时考虑多个相关结果及其排名；
- Recall 适合衡量“有没有召回”；
- MRR/NDCG 适合衡量“排得是否靠前”。

### 16.3 如何定位问题

```text
Candidate Recall@100 低
→ 切块、查询改写、BM25/向量召回或权限范围问题

Candidate Recall@100 高，Final Recall@8 低
→ 重排、去重、父块限制或最终截断问题

父块命中但答案要点覆盖低
→ 父块切分、相邻上下文或上下文预算问题

证据充分但答案错误
→ prompt、模型生成或引用校验问题
```

## 17. 当前项目结论

当前项目已经具备生产 RAG 的主要骨架：

- 父子块索引和来源回链；
- BM25 + 向量混合召回；
- RRF 融合；
- 查询改写和多意图候选；
- Cross-Encoder 重排及本地降级；
- 父块上下文扩展；
- 用户和课程权限隔离；
- 离线 Recall/MRR/NDCG 评测。

当前最明确的优化方向是：

1. 提升数字、位宽和上下文前缀的排序稳定性；
